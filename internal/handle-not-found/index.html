Go の NotFound（対象が見つからなかった）実装パターン

PostgreSQL / Redis に実際に接続してエラーを発生させ、OSS / ライブラリの実装パターンを比較する。

はじめに

「対象が見つからなかった」という状況をコードで表現する方法は、Go でも一つではない。 本レポートは internal/handle-not-found/main.go で実際に動作させたパターンを、 エラー型を使う表現、エラー型を使わない表現、 インターフェース層で実装側に押し付ける表現 に分けて解説する。

1. エラー型を使う表現

取得処理が失敗する可能性を表現したい場合、最も一般的な方法。 errors.Is / errors.As と組み合わせて使う。

1.1 センチネルエラー errors.Is

パッケージレベルの変数として「見つからなかった」ことを表す定数を定義し、 errors.Is(err, ErrNotFound) で判定する。 database/sql gorm mongo-driver go-redis 

var ErrNotFound = errors.New("not found")

// database/sql.ErrNoRows = errors.New("sql: no rows in result set")
// gorm.ErrRecordNotFound = errors.New("record not found")
// mongo.ErrNoDocuments   = errors.New("mongo: no documents in result")
// redis.Nil              = errors.New("redis: nil")

main.go では PostgreSQL から存在しない ID を取得した際に内部で発生する sql.ErrNoRows を、自前の ErrNotFound 系に変換してハンドリングしている。

参照: go/src/database/sql/sql.go (ErrNoRows), gorm.io/gorm/logger/logger.go (ErrRecordNotFound), go.mongodb.org/mongo-driver/mongo/single_result.go (ErrNoDocuments), github.com/redis/go-redis (Nil)

1.2 型付きエラー errors.As

エラーにリソース種別や ID などのメタデータを持たせる。 k8s.io/apimachinery ent 

type NotFoundError struct {
    Resource string
    Name     string
}

func NewNotFoundError(resource, name string) *NotFoundError {
    return &NotFoundError{Resource: resource, Name: name}
}

func (err *NotFoundError) Error() string {
    return fmt.Sprintf("%s %q not found", err.Resource, err.Name)
}

func IsNotFound(err error) bool {
    var target *NotFoundError
    return errors.As(err, &target)
}

errors.As を使うため、fmt.Errorf("...: %w", err) でラップされていても判定できる。

参照: k8s.io/apimachinery/pkg/api/errors/errors.go (NewNotFound, IsNotFound), ent/entc/gen/template/base.tmpl (NotFoundError)

1.3 ErrorCode / ErrorFault 付きの型付きエラー

AWS SDK v2 (smithy) のエラー型と同じ API を持たせる。 ErrorCode() でエラーコード文字列、ErrorFault() でクライアント/サーバー起因を返す。 aws-sdk-go-v2 

func (err *NotFoundError) ErrorCode() string {
    return "NotFoundError"
}

func (err *NotFoundError) ErrorFault() ErrorFault {
    return FaultClient
}

参照: github.com/aws/aws-sdk-go-v2/service/dynamodb/types/errors.go (ResourceNotFoundException 等), smithy-go

1.4 Is メソッドでのエラーコード → ドメイン概念のマッピング

標準ライブラリの syscall.Errno.Is と同じ思想。 低レイヤーのエラーコードを高レイヤーのドメイン概念にマッピングする。 syscall.Errno

例: ENOENT は fs.ErrNotExist と等価、EACCES/EPERM は fs.ErrPermission と等価。 

func (err *NotFoundError) Is(target error) bool {
    if target == ErrNotFound {
        return true
    }
    t, ok := target.(*NotFoundError)
    if !ok {
        return false
    }
    return err.Resource == t.Resource
}

main.go では PostgreSQL の SQLSTATE 42P01（undefined_table）を MapPQError で NotFoundError に変換している。

参照: go/src/syscall/syscall_unix.go (Errno.Is), github.com/lib/pq/error.go (*Error.SQLState)

1.5 MaskNotFound によるマスク

ent の MaskNotFound と同じ。NotFound エラーをあえて nil に変換する。 ent 

func MaskNotFound(err error) error {
    if IsNotFound(err) {
        return nil
    }
    return err
}
使いどころ 存在確認が目的で、呼び出し側が「無かった」ことを通常の成功と同等に扱いたい場合。

参照: ent/entc/gen/template/base.tmpl (MaskNotFound)

1.6 HTTP ステータスへの変換

ドメイン層のエラー表現を、HTTP レイヤーで 404 に変換する。 

func ToHTTPStatus(err error) int {
    switch {
    case errors.Is(err, ErrNotFound),
        errors.Is(err, sql.ErrNoRows),
        errors.Is(err, redis.Nil),
        errors.Is(err, fs.ErrNotExist):
        return http.StatusNotFound
    default:
        return http.StatusInternalServerError
    }
}

参照: k8s.io/apimachinery/pkg/api/errors/errors.go (NewNotFound は http.StatusNotFound を含む), go/src/net/http/server.go (http.NotFound)

2. エラー型を使わない表現

NotFound は必ずしも「エラー」として扱う必要はない。 Go では zero value / comma ok / 空コレクション / Null 型などで表現できる。

2.1 comma ok: (T, bool)

値と存在有無を同時に返す。Go の map アクセスや os.LookupEnv、sync.Map.Load と同じ。 os.LookupEnv sync.Map samber/lo 

func (r *UserRepo) LookupByID(ctx context.Context, id string) (*User, bool) {
    u, err := r.queryUser(ctx, id)
    if err != nil {
        return nil, false
    }
    return &u, true
}

user, ok := repo.LookupByID(ctx, id)
if !ok {
    // 見つからなかった
}

参照: go/src/os/env.go (LookupEnv), go/src/sync/map.go (Map.Load), github.com/samber/lo/find.go (Find)

2.2 Option 型

samber/mo の Option[T] と同じ API。 Some/None で存在を型として表現する。 samber/mo 

type Option[T any] struct {
    isPresent bool
    value     T
}

func Some[T any](value T) Option[T]
func None[T any]() Option[T]
func (o Option[T]) IsSome() bool
func (o Option[T]) IsNone() bool
func (o Option[T]) Get() (T, bool)

FindByID は見つからない場合に None[User]() を返す。 エラー型を使わないので、エラー処理が不要なパスで有効。

参照: github.com/samber/mo/option.go (Option[T]); 源流として Rust std::option::Option, Java java.util.Optional

2.3 存在確認 API の分離

「取得する」と「存在するかどうか」を別 API にする。 viper.IsSet などの流儀。 spf13/viper 

func (r *UserRepo) Exists(ctx context.Context, id string) (bool, error) {
    var exists bool
    err := r.db.QueryRowContext(ctx,
        "SELECT EXISTS (SELECT 1 FROM users WHERE id = $1)", id).Scan(&exists)
    return exists, err
}

参照: github.com/spf13/viper/viper.go (IsSet), github.com/redis/go-redis/v9/commands.go (Exists)

2.4 空コレクションを返す

一覧取得系では 0 件も正常な結果として空のスライスを返す。 mongo.Find、database/sql の Rows ループと同じ。 mongo-driver 

func (r *UserRepo) List(ctx context.Context) ([]User, error) {
    // ...
    users := make([]User, 0)
    for rows.Next() {
        // ...
        users = append(users, u)
    }
    return users, rows.Err()
}
ポイント 0 件は「NotFound」ではなく「結果が空」という解釈にする。呼び出し側は len(users) == 0 で判定する。

参照: go.mongodb.org/mongo-driver/mongo/collection.go (Find), go/src/database/sql/sql.go (Rows)

2.5 番兵値

値がないことを特殊な値で表す。 strings.Index は見つからない場合に -1 を返す。 Redis の EXISTS は存在数を 0 で返す。 strings redis 

if strings.Index("a,b,c", "z") == -1 {
    // 見つからなかった
}

if n, _ := rdb.Exists(ctx, key).Result(); n == 0 {
    // キーが存在しない
}

参照: go/src/strings/strings.go (Index), github.com/redis/go-redis/v9/commands.go (Exists)

2.6 Null 型

sql.NullString などで「値が設定されていない」を表現する。 JSON の null と同じ意味論。 database/sql 

var nickname sql.NullString
rows.Scan(&nickname)

if !nickname.Valid {
    // 値が NULL → 未設定
}

参照: go/src/database/sql/sql.go (NullString, NullInt64 等)

2.7 http.NotFound helper

HTTP 層ではエラー型を経由せず、直接レスポンスに 404 を書く。 net/http 

rec := httptest.NewRecorder()
http.NotFound(rec, r)
// rec.Code == 404

参照: go/src/net/http/server.go (NotFound, NotFoundHandler)

3. インターフェース層で NotFound を実装側に押し付ける

インターフェースを挟むと、「NotFound をどう表現するか」を実装側に委ねられる。 呼び出し側は IsNotFound(err) などの統一判定だけを使い、実装の詳細を知らなくて済む。

3.1 インターフェース契約

UserStore インターフェースは「見つからない場合は NotFound 系エラーを返す」ことを約束する。 実装側がセンチネルでも型付きでも自前の型でもよい。 

type UserStore interface {
    Get(ctx context.Context, id string) (*User, error)
    Exists(ctx context.Context, id string) (bool, error)
    Lookup(ctx context.Context, id string) (*User, bool, error)
}

参考: ent/entc/integration/ent/client.go (UserClient.Get は *NotFoundError を返す契約), gorm.io/gorm/finisher_api.go (*DB.First/Last/Take は ErrRecordNotFound を返す契約)

3.2 センチネル契約（方法1）

パッケージが ErrNotFound を公開し、実装側は %w でラップして返す。 文脈付与は実装側の裁量。 

func (s *RedisUserStore) Get(ctx, id) (*User, error) {
    if errors.Is(err, redis.Nil) {
        return nil, fmt.Errorf("redis store: %w", ErrNotFound)
    }
    // ...
}

参照: gorm.io/gorm/finisher_api.go (*DB.First/Last/Take が ErrRecordNotFound を返す)

3.3 型付きエラー契約（方法2）

実装側は NotFoundError を使って「どのリソースが無いか」を返す。 呼び出し側は errors.As でメタデータを取り出せる。 

func (s *PostgresUserStore) Get(ctx, id) (*User, error) {
    return s.repo.GetByID(ctx, id)  // NotFoundError をそのまま伝搬
}

参照: ent/entc/integration/ent/client.go (UserClient.Get), ent/entc/gen/template/base.tmpl (NotFoundError)

3.4 自己申告契約（方法3）

実装側が自前のエラー型を作る場合、NotFound() bool を実装して自己申告する。 AWS SDK v2 の ErrorFault() や gRPC の codes.NotFound と同じ思想。 

type NotFoundReporter interface {
    error
    NotFound() bool
}

type articleNotFoundError struct{ id string }
func (e *articleNotFoundError) NotFound() bool { return true }

参照: github.com/aws/aws-sdk-go-v2/service/dynamodb/types/errors.go (ErrorCode / ErrorFault), k8s.io/apimachinery/pkg/api/errors/errors.go (IsNotFound は StatusError を errors.As で判定)

3.5 シグネチャで強制（方法4/5）

Exists（存在確認）と Lookup（comma ok）をインターフェースに含める。 実装側はメソッド実装によって「無いことをどう表現するか」を強制される。 

type UserStore interface {
    Get(ctx, id) (*User, error)
    Exists(ctx, id) (bool, error)           // 方法4: 存在確認を分離
    Lookup(ctx, id) (*User, bool, error)    // 方法5: comma ok を強制
}

純粋な comma ok (T, bool) は「エラーが起こり得ない操作」（map アクセスなど）に向く。 DB/Redis のような失敗しうる操作では (T, bool, error) にして、 NotFound だけを false で表現しつつエラーを伝搬させる。

参照: go/src/sync/map.go (Map.Load), go/src/os/env.go (LookupEnv), github.com/spf13/viper/viper.go (IsSet), github.com/redis/go-redis/v9/commands.go (Exists)

3.6 3契約を横断判定する IsNotFound

呼び出し側は1つの関数で3系統の実装を判定できる。 

func IsNotFound(err error) bool {
    if errors.Is(err, ErrNotFound) { return true }       // 方法1: センチネル
    var nf *NotFoundError
    if errors.As(err, &nf) { return true }               // 方法2: 型付き
    var r NotFoundReporter
    if errors.As(err, &r) && r.NotFound() { return true } // 方法3: 自己申告
    return false
}

参考: k8s.io/apimachinery/pkg/api/errors/errors.go (IsNotFound は errors.As ベースの横断判定)

3.7 conformance 契約テスト（方法6）

静的には「実装が契約を守るか」を強制できないため、テストで担保する。 全実装を同一テストに通すことで、差し替えても挙動が変わらないことを保証する。 

func AssertUserStore(store UserStore, missingID string) error {
    if _, err := store.Get(ctx, missingID); !IsNotFound(err) {
        return fmt.Errorf("Get must return NotFound, got %v", err)
    }
    if exists, err := store.Exists(ctx, missingID); err != nil || exists {
        return fmt.Errorf("Exists must be (false, nil), got (%v, %v)", exists, err)
    }
    if u, ok, err := store.Lookup(ctx, missingID); err != nil || ok {
        return fmt.Errorf("Lookup must be (nil, false, nil), got (%v, %v, %v)", u, ok, err)
    }
    return nil
}
ポイント 実運用では AssertUserStore は _test.go に置き、各実装に対して同じテストを適用する。

参考: Go 標準ライブラリでは database/sql driver tests 等で、同一 interface を実装する複数ドライバーに対して同じ conformance test を適用する形で使われている。

5. 使い分けの指針

  • ドメイン/データ層の失敗を呼び出し側に知らせたい → センチネルエラーまたは型付きエラー。
  • エラーに原因やリソース名を含めたい → 型付きエラー (NotFoundError)。
  • マイクロサービス/外部 API でエラーを分類したい → ErrorCode() / ErrorFault() 付き。
  • 存在確認だけで「無い」ことを正常値としたい → comma ok / Option / Exists / MaskNotFound。
  • 一覧取得 → 空コレクションを返す。
  • HTTP 層の最終出力 → http.NotFound または ToHTTPStatus。
  • 実装を差し替え可能にしたい → インターフェース + IsNotFound による統一判定。
  • インターフェース契約を守らせたい → AssertXxx による conformance テスト。

6. まとめ

NotFound は「エラー」として扱うか、「値の不在」として扱うかで実装が大きく変わる。 Go では errors.Is / errors.As によるエラー判定が標準的だが、 comma ok、Option[T]、空コレクション、番兵値、Null 型など、 エラー型を使わない選択肢も豊富にある。

さらに、インターフェースを挟めば「NotFound の表現」を実装側に押し付け、 呼び出し側をシンプルに保つこともできる。 重要なのは、ライブラリやレイヤーごとに一貫したルールを決め、 呼び出し側が「見つからない」ことを予測可能に検知できるようにすること。
